## DEF-001: quantityの全角数字が意図せず受理される可能性

- **発見日**: 2026-07-26
- **検出手段**: 実装前の仕様確認（models.py実装前にPython標準動作を手動検証）。
- **再現手順**: Pythonの対話環境で `int('５')` を実行する。
- **期待**: 全角数字は無効な入力として拒否されるべき（同値分割 EQ-QTY-02の設計意図）。
- **実際**: Python標準の `int()` は全角数字（Unicode digit）を暗黙に半角へ変換して受理する（`int('５') == 5`）。何も対策しないと、全角数字混入データが検証をすり抜ける。
- **原因分析**: CPythonの `int()` はUnicodeの数字カテゴリを解釈するため、ASCII以外の数字表現も受理する仕様になっている。業務データ（Excel由来など）では全角数字の混入が起こり得るため、明示的な制御が必要だった。
- **修正**: `validate_quantity` にASCII半角数字のみを許可する正規表現(`_ASCII_INT_PATTERN = r"^[+-]?[0-9]+$"`)による事前チェックを追加し、`int()`の暗黙変換に頼らないようにした。
- **追加した回帰テスト**: `tests/test_models.py::test_validate_quantity_rejects_fullwidth_explicitly`、`test_validate_quantity_invalid[EQ-QTY-02-fullwidth]`。

## DEF-002: unit_priceの全角数字チェックが正規表現の書き方により漏れていた

- **発見日**: 2026-07-26
- **検出手段**: `tests/test_models.py::test_validate_unit_price_invalid[EQ-PRICE-02-fullwidth]` の実行（pytest）で検出。
- **再現手順**: `validate_unit_price('１２００')`（全角の1200）を呼び出す。
- **期待**: 全角数字は無効として拒否される（DEF-001と同じ設計意図をunit_priceにも適用したはず）。
- **実際**: `Decimal('1200')` が返り、有効な値として受理されてしまった（テストが `AssertionError: assert Decimal('1200') is None` で失敗）。
- **原因分析**: DEF-001の対策として書いた正規表現 `_ASCII_DECIMAL_PATTERN` が `r"^[+-]?(\d+\.?\d*|\.\d+)$"` となっており、`\d` を使っていた。Pythonの正規表現では `re.ASCII` フラグを付けない限り `\d` はUnicodeの数字カテゴリ（全角数字を含む）にマッチするため、ASCII限定のつもりが実際は限定できていなかった。quantity側は `[0-9]` と明示していたため同じ問題を回避できていた（実装の一貫性不足が原因）。
- **修正**: `_ASCII_DECIMAL_PATTERN` を `\d` から明示的な `[0-9]` に変更（`r"^[+-]?([0-9]+\.?[0-9]*|\.[0-9]+)$"`）。
- **追加した回帰テスト**: 既存の `test_validate_unit_price_invalid[EQ-PRICE-02-fullwidth]` がそのまま回帰テストとして機能する（当初レッドで検出→修正でグリーンに）。

## DEF-003: mutmutがネイティブWindowsで動作しない

- **発見日**: 2026-07-26
- **検出手段**: `mutmut --help` の実行（ローカル開発機・Windows）。
- **再現手順**: Windows上（WSLなし）で `python -m mutmut run` を実行する。
- **期待**: ミューテーションテストが実行され、スコアが得られる。
- **実際**: 「To run mutmut on Windows, please use the WSL.」と表示され実行不可。当該機にはWSL自体が未導入（`wsl --status`が失敗）。
- **原因分析**: mutmutはネイティブWindowsを公式サポートしておらず、WSL経由の実行を前提とするツールである（コード側の不具合ではなく環境制約）。実装ソース(`mutmut/__main__.py`の`run`コマンド)を確認したところ、ミュータント実行の並列化に`os.fork()`を使用しており、これはPOSIX専用でWindowsには存在しない機構であるため、表面的な制限ではなく実装上の根本的な制約と判明した。WSL導入はシステム全体に影響する変更のため、この検証タスクの範囲では実施しないと判断した。
- **対応**: ①CI（GitHub Actions・Ubuntuランナー）の`mutation.yml`で実際にmutmutを実行し、真のミューテーションスコアはそちらで取得する。②ローカルでは代替として、リスクの高い8箇所（金額計算・境界値・CSVインジェクション対策・原子的書き込み・CLI終了コード分岐・文字コードフォールバック・重複明細の合算・集計の並び順）に対して**手動ミューテーション**（一時的にロジックを壊す→テスト実行→検知確認→元に戻す）を実施し、8/8件をテストスイートが検知することを確認した（詳細は`docs/test-report.md`）。
- **追加した回帰テスト**: 手動ミューテーションはコードへの恒久変更を伴わないため新規テストは追加していない（既存テストの検知力を確認しただけ）。

## DEF-004: ブランチ名とCIトリガー設定の不一致によりCIが起動しない

- **発見日**: 2026-07-26
- **検出手段**: **公開前レビューでの指摘**（「スキップしたものは無いか」という問いを受けて未検証項目を洗い出す過程で発見）。自動テストでは検知できない種類の欠陥。
- **再現手順**: `git init`で作られた既定ブランチ（`master`）のままリポジトリをGitHubへpushする。
- **期待**: pushをトリガーに`ci.yml`（マトリクステスト）・`security.yml`が起動し、品質ゲートが機能する。
- **実際**: 各ワークフローのトリガーが `on: push: branches: [main]` と`main`固定だったため、`master`へのpushでは**どのワークフローも起動しない**。テスト・lint・型チェック・セキュリティスキャン・ミューテーションテストという品質ゲートが全て沈黙し、しかも「失敗」ではなく「何も走らない」ため気づきにくい。
- **原因分析**: `git init`の既定ブランチ名（環境により`master`）と、ワークフロー側で想定した`main`を突き合わせていなかった。CIを実際に一度も動かさずに「設定完了」とみなしたことが根本原因（＝**設定を書いた≠設定が動く**）。
- **修正**: `git branch -m master main` でブランチ名を`main`に統一した。
- **追加した回帰テスト**: この種の設定不整合はユニットテストでは検知できない。代替として**「CIが実際に緑になるのを目視確認するまで公開完了とみなさない」**を受け入れ手順に組み込む（`docs/test-report.md` §6のリリース判断条件に反映）。

## DEF-005: トレーサビリティ表に実在しないテスト関数名が記載されていた

- **発見日**: 2026-07-26
- **検出手段**: **公開前レビューでの指摘**を受けた自己点検。設計書記載の関数名で`grep`したところ1件もヒットしなかった。
- **再現手順**: `docs/test-design.md` §5の表にある `test_row_validation` / `test_load_encoding` / `test_cli_exit_codes` / `test_cli_output_options` / `test_aggregate_boundary_values` を`tests/`配下で検索する。
- **期待**: 表に書かれた観点ID→テスト関数の対応が実装と一致している（表の目的そのもの）。
- **実際**: 上記の関数名はいずれも実在せず、実装では`test_validate_quantity_valid[EQ-QTY-01]`等の別の命名になっていた。**トレーサビリティ表という「差別化の看板」が実態と乖離**していた。
- **原因分析**: 設計段階で書いた表を「実装完了時に更新する」と設計書自身に明記していたにもかかわらず、その更新工程を実行しなかった。設計→実装で命名方針を変えた（モジュール単位の関数名＋parametrize IDに観点IDを埋め込む方式に変更した）のに、上流ドキュメントへ反映しなかったのが直接原因。
- **修正**: §5の表を実際のテスト関数名・ファイルで全面的に書き換えた。あわせて**parametrizeのテストIDに観点IDを埋め込む方式**を明記し、`pytest -k "EQ-QTY"`のように観点IDで実際に絞り込めることを検証した（EQ-QTY=7件、BV-SEC=9件、dt2=5件が正しく選択されることを確認）。これにより表と実装の乖離が起きにくくなった。
- **追加した回帰テスト**: ドキュメント整合性の自動検証は未導入（残存リスクに記載）。ただし観点IDでの絞り込みが機能することを確認したため、表の妥当性は`pytest -k`で随時検証できる。

## DEF-006: 列数がヘッダ未満のCSV行でクラッシュする（3レビュー全員が指摘）

- **発見日**: 2026-07-26
- **検出手段**: 公開前の3種レビュー（Opus再確認・別コンテキストOpus・Codex）が**全員独立に**発見。CEOによる「他にスキップしたものは無いか」という問いを起点に多角レビューを実施した結果。
- **再現手順**: ヘッダが`date,store,product,quantity,unit_price`（5列）のCSVに対し、`2026-01-01,渋谷店,商品A`（3列）のような列数不足の行を含める。
- **期待**: 不足したフィールドは検証エラーとして扱われ、行エラーとして記録される（他の行の処理は継続される）。
- **実際**: `csv.DictReader`が列数不足の行の欠損フィールドを既定で`None`埋めし、`parse_row`が`raw.get(key, "")`で取得した値（`None`）に対し`validate_*`関数内で`value.strip()`を呼び出し、**`AttributeError: 'NoneType' object has no attribute 'strip'`で未捕捉のままCLI全体がクラッシュ**していた。
- **原因分析**: `raw.get(key, "")`の第2引数（デフォルト値）は「キーが存在しない場合」にのみ効く。`csv.DictReader`は列数不足の行でもキー自体は存在させ値だけを`None`にするため、このデフォルト値が機能しなかった。**このツールが掲げる差別化「1ファイル・1行の事故で全体を止めない」という設計原則に反する、最も現実的に起きる壊れ方**（途中で切れたエクスポート・手編集で壊れたCSV）でその機能が破綻していた。カバレッジ100%・プロパティテスト・ゴールデンテストを含む122件の既存テストは全て整形済みの行しか入力していなかったため、この欠陥を1件も検出できていなかった。
- **修正（二重の防御）**: ①`loader.py`の`csv.DictReader`に`restval=""`を指定し、列数不足時の欠損値を`None`ではなく`""`にする。②`models.py`に`_get_str()`ヘルパーを追加し、`raw.get(key)`が`None`を返した場合も`""`として扱う防御を`parse_row`内に実装（loaderの`restval`設定だけに依存しない二重の安全策）。
- **追加した回帰テスト**: `tests/test_loader.py::test_load_file_short_row_is_recorded_as_error_not_crash`（列数不足行が行エラーとして記録され後続行の処理が継続すること）、`tests/test_loader.py::test_load_file_excess_columns_are_ignored_safely`（列数過剰行は安全に無視されること）、`tests/test_models.py::test_parse_row_handles_none_values_without_crashing`（`_get_str`の防御を直接検証）。**修正前コードに戻して両テストが実際に赤（AttributeError）になることを確認済み**。
- **教訓**: 「カバレッジ100%」は同値クラスとして存在する分岐が全て通ったことしか意味しない。**そもそもテスト設計の観点自体に存在しない同値クラス（フィールドの欠落）はカバレッジで検出できない**。`docs/test-design.md` DT-1に「フィールドの存在有無」という軸を追加した。

## DEF-007: エラーCSVのファイルパス列がCSVインジェクション無害化から漏れていた（3レビュー全員が指摘）

- **発見日**: 2026-07-26
- **検出手段**: 公開前の3種レビュー（Opus再確認・別コンテキストOpus・Codex）が全員独立に指摘。`render_errors_csv`のコードを読み、`reason`列は`sanitize_csv_field()`で無害化されているのに`fe.path`/`re_.file`（ファイルパス列）はそのまま`str()`で出力されていることに気づいた。
- **再現手順**: ファイル名が`=cmd|calc.csv`のような、CSVインジェクションの接頭辞（`=` `+` `-` `@`）で始まるファイルを`FileError`または`LoadedRowError`として`render_errors_csv()`に渡す。
- **期待**: `docs/test-design.md` §1.3「CSVインジェクション対策」は「CSV出力時、フィールド値が`=` `+` `-` `@`またはタブ/CRで始まる場合、先頭に`'`を付与して無害化する」と規定しており、**出力される全ての文字列セルに一貫して適用される**べき。
- **実際**: `reason`列（不具合の理由）は`sanitize_csv_field()`でラップされていたが、**ファイルパス列だけラップされておらず素通し**になっていた。ファイル名は攻撃者が制御し得る値であり（Linux等では`=evil.csv`のようなファイル名を実際に作成できる）、そのファイルがエラー対象になった場合、生成されたエラーレポートCSVをExcel等で開くと数式が実行され得る。
- **原因分析**: `reason`列の無害化を実装した際、「ユーザーが入力した自由記述の値」という意識で`reason`だけを対象にし、「ファイルパスも外部から渡ってくる文字列である」という点を見落としていた。CSVインジェクション対策は「危険そうな列だけ」でなく「**出力する全ての文字列セル**」に機械的に適用しないと、対策として不完全になる典型例。
- **修正**: `report.py`の`render_errors_csv()`で、`fe.path`・`re_.file`も`sanitize_csv_field()`でラップするよう変更。
- **追加した回帰テスト**: `tests/test_report.py::test_render_errors_csv_sanitizes_file_path_column`。危険な接頭辞（`=`・`+`）で始まるファイル名を`FileError`・`LoadedRowError`双方に与え、出力されたCSVのパス列が無害化されていることを検証する。**修正前コードに戻すと実際に赤（パス列が無害化されずに素通り）になることを確認済み**。
- **教訓**: セキュリティ対策を「危険と分かっている列だけ」に個別適用すると、後から追加された列（この場合はパス列）が対策の対象から漏れやすい。理想的には「出力する文字列セルは全て無害化関数を通す」という一律のルールにする方が、対策漏れを構造的に防げる。

## DEF-008: 書込失敗時、設計書が約束したexit 2にならない（別コンテキストレビューが指摘）

- **発見日**: 2026-07-26
- **検出手段**: 公開前の別コンテキストOpusレビュー。実機で「出力先の親ディレクトリが書込不可（既存ファイルのパス）」を再現し発見。
- **再現手順**: `--output`に、親ディレクトリの位置に通常ファイルが存在するパスを指定する（例: `blocker`という名前のファイルがある状態で`--output blocker/summary.md`）。
- **期待**: `docs/test-design.md` §1.4 と README で明記した「出力先に書き込めない → exit 2（入力・利用方法エラー）」という終了コードの契約どおりに動作する。
- **実際**: `write_atomic`の呼び出しが`try`で囲まれておらず、生の`OSError`（Windowsでは`FileExistsError [WinError 183]`）がそのままCLIの外まで伝播し、typerが自動的にtracebackを表示したうえで**exit 1**（有効明細0件の意味）で終了していた。cron等の自動化から呼び出した場合、「書込に失敗した」という重大な事象が「処理対象データが無かっただけ」という軽微な事象として誤認・黙殺される。
- **原因分析**: `cli.py`内の2箇所（サマリレポート・エラーレポートそれぞれの`write_atomic`呼び出し）で、ファイルI/Oが失敗し得るという前提が実装時に考慮されていなかった。設計書に明記した終了コードの契約と実装が一致しているかを、実際に書込失敗を発生させて確認する検証が抜けていた。
- **修正**: `cli.py`の両方の`write_atomic`呼び出しを`try/except OSError`で囲み、ユーザー向けメッセージを表示したうえで`typer.Exit(EXIT_USAGE_ERROR)`（exit 2）を送出するように変更。
- **追加した回帰テスト**: `tests/test_cli.py::test_dt2_06_output_write_failure_exits_usage_error_not_no_data`、`test_dt2_06_report_errors_write_failure_exits_usage_error`。両テストとも、出力先の親ディレクトリの位置に通常ファイルを配置することで実際の書込失敗を再現している（モックではなく実ファイルシステムでの検証）。**修正前コードに戻すと`exit_code == 1`かつ生の`FileExistsError`が露出することを確認済み**。
- **教訓**: 設計書に書いた「終了コードの契約」は、それを破る具体的な入力（この場合は書込不可のパス）を用意して実際に検証するまで、本当に守られているか分からない。ドキュメントの記述と実装の一致は、DEF-005（トレーサビリティ表の乖離）と同種の「書いた≠実装されている」問題である。

## DEF-009: 入力=出力を指定すると元データが破壊される（Codex Critical#2）

- **発見日**: 2026-07-26
- **検出手段**: 公開前のCodexレビューが指摘。CEOによる指摘を受けてOpusが実機で再現確認した。
- **再現手順**: `sales-report --input sales.csv --format csv --output sales.csv` のように、入力ファイルと同一パスを`--output`に指定して実行する。または`--output`と`--report-errors`に同一パスを指定する。
- **期待**: 入力と出力の衝突は検出され、実行前に拒否される（または少なくとも元データを保持したまま安全にエラーになる）。
- **実際**: 検証・拒否のロジックが一切無く、CLIは**正常終了（exit 0）**したうえで、元の入力CSVの内容が集計結果（サマリ）で**完全に上書きされて消える**。エラーメッセージも警告も出ないため、利用者は気づかないまま元データを失う。
- **原因分析**: 実装時、「1ファイルの処理中に自分自身を壊すか」という観点でしか検証していなかった（Sonnetの探索的テスト`docs/exploratory-notes.md`セッション2で「自己上書きは安全」と誤って結論づけていた）。実際には「全読込→集計→書込」の順序を守っているため**処理中にクラッシュはしない**が、**書込の瞬間に元データを意図せず上書きする**という、クラッシュとは全く別種の被害があることを見落としていた。「安全」の定義を①クラッシュしないこと、の1点だけで判定し、②データが破壊されないこと、を確認していなかった。
- **修正**: `cli.py`に`_find_path_collision()`関数を追加し、`--input`（ファイルまたはその配下のディレクトリ）と`--output`／`--report-errors`が衝突する3パターン（入力ファイル=出力、出力が入力ディレクトリの中、出力=エラーレポート出力）を実行前に検査。衝突時はexit 2で処理を中断し、**入力データは一切変更されない**。パス比較は`Path.resolve()`で正規化してから行う。
- **追加した回帰テスト**: `tests/test_cli.py::test_fix03_input_file_equals_output_is_rejected_and_data_preserved`（元データのバイト内容が変化していないことまで検証）、`test_fix03_output_inside_input_directory_is_rejected`、`test_fix03_output_equals_report_errors_is_rejected`、`test_fix03_normal_separate_paths_still_succeed`（誤検知が無いことの確認）。**修正前コードに戻すと3件とも赤（exit 0のまま元データが上書きされる）になることを確認済み**。
- **副次的な発見①**: 既存の`tests/test_robustness.py::test_idempotent_reruns_with_directory_input_and_multiple_files`が、出力先を入力ディレクトリの直下に置いていたため、この修正によって（正しく）exit 2で落ちるようになった。これは元々「2回目の実行が1回目の出力を入力として誤って拾う」という欠陥をテストが検出できていなかった証拠でもある（別コンテキストレビュー・Codex双方が指摘）。テストの入出力ディレクトリを兄弟関係に分離して修正した。
- **副次的な発見②**: ①のテスト修正後、`cli.py`のカバレッジが100%から92%へ低下した。原因を調査したところ、①の欠陥テストが「2回目の実行で1回目の出力をファイルレベルエラーとして拾う」経路を**偶然**通っていたため、CLIレベルの「ファイルを読み込めませんでした」という警告表示の唯一のカバレッジ源になっていたと判明した。欠陥テストを正しく直したことで、その偶然のカバレッジも同時に失われた。**「テストが通っている」ことと「意図した観点を検証できている」ことは別**という、このレビュー全体を貫く教訓の縮図。`tests/test_cli.py::test_cli_warns_about_file_level_error_but_still_succeeds`として意図的なテストに置き換えた。
- **教訓**: 探索的テストで「安全」と判定するときは、①クラッシュしないこと ②入力データが変更・破壊されないこと ③出力が期待通りであること、を**分けて**確認する。1つの観点だけで「安全」と結論づけると、この事例のように最も重大な観点（データ損失）を見落とす。

## DEF-010: Decimal既定精度28桁超で例外なく金額が誤計算される（Codex High#3）

- **発見日**: 2026-07-26
- **検出手段**: 公開前のCodexレビュー。入力桁数に上限が無い一方、Decimal演算は既定コンテキストで精度28桁に制限されることを指摘し、実測で再現。
- **再現手順**: `SaleRow(quantity=9, unit_price=Decimal("99999999999999999999999999999"))`（29桁の単価）の`.amount`を計算する。
- **期待**: 金額計算に丸め誤差が生じない（`docs/test-design.md` §1.1「金額計算はDecimal同士の演算のみで行い丸め誤差を出さない」という設計原則どおり）。
- **実際**: `9 × 99999999999999999999999999999` の正しい値は`899999999999999999999999999991`だが、実際に得られた値は`900000000000000000000000000000`（9円多い）。**例外も警告も一切出ない**まま静かに誤った金額が返る。さらに複数行を合算する`aggregate()`でも、大量の高額行を足し合わせると同様に丸め誤差が蓄積することを確認した（100,001件の上限値ぎりぎりの明細を合算する実験で、既定精度28桁では実際に丸め誤差が発生し、精度50桁では発生しないことを二分探索で特定・実証した）。
- **原因分析**: `decimal`モジュールの既定コンテキストは精度28桁（有効桁数）に制限されている。実装当初、金額計算を「Decimalを使っているから正確」という前提だけで済ませており、**入力の桁数に上限を設けていなかった**ため、大桁の値や大量行の合算という現実的にあり得る入力で精度上限を超過するケースを見落としていた。
- **修正（2段構え）**: ①入力段階で桁数上限を設ける — `unit_price`は整数部12桁・小数部2桁まで、`quantity`は9桁（10億未満）までとし、超過は行エラーとして拒否する（`models.py`の`validate_quantity`/`validate_unit_price`）。②`aggregate()`全体を`decimal.localcontext()`で精度50桁に引き上げて実行し、桁数上限ぎりぎりの明細を大量に合算しても丸めが起きない余裕を持たせる（`with`ブロック内のみ有効で、他コードへの副作用は無い）。
- **追加した回帰テスト**: `tests/test_models.py`に桁数境界のテスト（quantity 9桁OK/10桁NG、unit_price整数部12桁OK/13桁NG、小数部2桁OK/3桁NG）。`tests/test_aggregate.py::test_aggregate_no_rounding_at_large_scale_with_default_28_digit_precision_would_fail`は、桁数上限ぎりぎりの値を100,001件（二分探索で特定した閾値）合算し、整数演算による丸め無しの真値と一致することを検証する。**`aggregate()`から`localcontext(prec=50)`を外すと実際にこのテストが赤になる（丸め誤差が発生する）ことを確認済み**。
- **教訓**: 「Decimalを使っている」ことと「Decimalなら常に正確」は別。有限精度のコンテキストを持つ以上、桁数の上限を明示的に検討しない限り、どんな精度でもいつか超過し得る。テスト観点としても、境界値分析は「型が正しいか」だけでなく「その型が扱える範囲内か」まで踏み込む必要がある。

## DEF-011: Slack Webhook URL(秘密情報)がエラーメッセージ経由でログに漏洩する（Codex High#8）

- **発見日**: 2026-07-26
- **検出手段**: 公開前のCodexレビュー。`requests`のHTTPエラー文字列には通常URLが含まれ、Slack Webhook URLはURL自体がcredential（トークンをURLパスに埋め込む形式）であるため、エラー時にstderr/CIログへ漏洩し得ると指摘。
- **再現手順**: `send_slack_summary(webhook_url, result)`をHTTPエラー（500等）または接続エラーで失敗させ、送出される`NotifyError`のメッセージを確認する。`cli.py`は`except NotifyError as e: typer.echo(f"警告: {e}", err=True)`でこのメッセージをそのまま標準エラー出力に表示する。
- **期待**: 通知失敗時のメッセージに、Webhook URL（＝Slackアカウントに対する事実上の認証情報）が含まれない。
- **実際**: `notify.py`が`f"Slackへの通知に失敗しました: {e}"`という形で例外オブジェクトをそのまま文字列化しており、`requests`の例外（`HTTPError`・`ConnectionError`等）の標準的な文字列表現には接続先URL（Webhook URLそのもの、秘密のトークン部分を含む）が含まれるため、そのままstderrやCI実行ログに露出していた。
- **原因分析**: 例外を捕捉した際に「詳細情報を出す方が親切」という考えで`{e}`をそのまま埋め込んだが、**この例外の詳細情報自体に秘密情報が含まれる**という認識が抜けていた。一般に、外部サービスのURLに認証情報を埋め込む方式（Slack Incoming Webhook・多くのWebhook系API）では、URLそのものを機密として扱う必要がある。
- **修正**: `notify.py`で`requests.HTTPError`と`requests.RequestException`を分けて捕捉し、ユーザー向けメッセージには**HTTPステータスコードまたは例外の種別名のみ**を含める（URLやトークンを含む詳細文字列は含めない）。元の例外は`raise NotifyError(msg) from e`で例外チェーン（`__cause__`）として保持するため、必要であればPythonのtracebackやデバッガから追跡できるが、**通常のユーザー向け表示・ログには出ない**。
- **追加した回帰テスト**: `tests/test_notify.py`に秘密トークンを含む模擬Webhook URLを使ったテストを追加（`test_send_slack_summary_http_error_does_not_leak_webhook_url`、`test_send_slack_summary_connection_error_does_not_leak_webhook_url`）。例外メッセージにトークン・URLが含まれないことを直接アサートする。あわせて`test_send_slack_summary_original_exception_still_chained`で、表示上は秘密を隠しつつ原因追跡用の例外チェーンは保持されていることも検証。**修正前コードに戻すと両テストが実際に赤（トークンが露出）になることを確認済み**。
- **教訓**: 例外メッセージを「詳細だから親切」という理由でそのままユーザーに見せる実装は、詳細情報の中身を精査していないと危険。特に**URLに認証情報を埋め込む方式のAPI**（Slack/Discord Incoming Webhook、多くのSaaSのWebhook機能）を扱うコードでは、例外処理を書く際に「このエラーメッセージのどこかにURLが含まれていないか」を必ず確認する。

## DEF-012: 読込時のOSError(権限エラー等)が未捕捉で全体停止する（Codex #11）

- **発見日**: 2026-07-26
- **検出手段**: 公開前のCodexレビュー。「エンコーディング判定は`UnicodeDecodeError`しか捕捉していないため、読込中のOSError・権限エラー・ファイル消失はファイル単位エラーにならず全体を停止する」という指摘を受け実機で再現。
- **再現手順**: `unittest.mock`で`Path.read_text`が`PermissionError`を送出するようにし、`load_file()`を呼び出す。
- **期待**: 「1ファイルの事故で全体を止めない」という設計原則（README・test-design.mdに明記）どおり、当該ファイルのみファイルレベルエラーとして記録され、他のファイルの処理は継続される。
- **実際**: `_read_text_with_fallback()`が`UnicodeDecodeError`のみを`try/except`で捕捉しており、`PermissionError`等の`OSError`は未捕捉のまま`load_file()`・`load_files()`を通じてCLI全体まで伝播し、処理が完全に停止していた。
- **原因分析**: 「文字コード判定の失敗」（`UnicodeDecodeError`）と「そもそもファイルが読めない」（`OSError`）という**性質の異なる2種類の失敗モード**を、実装時に区別せず「デコード周りのエラー」として一括りに考えてしまっていた。「1ファイルの事故で全体を止めない」という設計原則を、文字コード判定という特定のシナリオにしか適用できていなかった。
- **修正**: `loader.py`の`load_file()`で`_read_text_with_fallback(path)`の呼び出しを`try/except OSError`で囲み、発生した場合はファイルレベルエラーとして記録して処理を継続する。`OSError`はエンコーディングと無関係なため、`_read_text_with_fallback`内部の複数エンコーディングを試すループでは捕捉せず、呼び出し側で一度だけ処理する設計にした（同じI/Oエラーがエンコーディングを変えても再現するだけで、リトライする意味が無いため）。
- **追加した回帰テスト**: `tests/test_loader.py::test_load_file_permission_error_becomes_file_error_not_crash`（単一ファイルでの検証）、`test_load_files_permission_error_on_one_file_does_not_stop_others`（複数ファイル中の1つが権限エラーでも、他の有効なファイルの処理が継続されることを検証）。**修正前コードに戻すと両テストが実際に赤（`PermissionError`が未捕捉で伝播）になることを確認済み**。
- **教訓**: 「例外を1種類だけ捕捉している」コードを見たら、「本当にその例外だけが起こり得るのか」を疑う。ファイルI/O関連の処理では、デコードエラー・権限エラー・ファイル消失・ディスクエラーなど**複数の異なる失敗モードが同じ操作（`read_text()`等）から起こり得る**ことを前提に設計する。

## DEF-013: 「関数は単体テスト済みだが配線が未検証」という構造的欠陥（別コンテキストレビューが手動ミューテーションで実測）

- **発見日**: 2026-07-26
- **検出手段**: 公開前の別コンテキストレビューが、`sanitize_csv_field()`・`escape_markdown_cell()`の呼び出し削除、`requests.post()`の`timeout`削除、Slack本文の店舗数/商品数行の削除、構造化ログの`skipped_rows`のハードコード化など、**手動ミューテーションを12箇所に仕込んで実測**したところ、**8箇所が全く検知されず生存**した（既存122件のテストが1件も落ちなかった）。
- **再現手順**: 例として、`report.py`の商品列レンダリングから`sanitize_csv_field(p.product)`を`p.product`に変更し、既存のテストスイート（当時122件）を実行する。
- **期待**: CSVインジェクション対策・Markdownエスケープ・タイムアウト設定など、セキュリティ・堅牢性に関わる処理の呼び出しを削除すれば、いずれかのテストが検知して失敗する。
- **実際**: 8箇所のミューテーションが**全て検知されずテストが緑のまま**だった。原因は共通していた: `sanitize_csv_field()`や`escape_markdown_cell()`自体は`tests/test_report.py`で**単体として**十分にテストされていたが、それが`render_csv_report()`・`render_markdown_report()`・`render_errors_csv()`の**内部で実際に呼ばれているか**（配線）は、既存のどのテストも直接検証していなかった。同様に、既存の`test_build_slack_payload_contains_totals`は`payload["text"]`に`"3"`が含まれるかを見ていたが、`"3"`は総数量の値と偶然一致するため、店舗数/商品数の行自体を削除しても偽陽性のまま通過していた。構造化ログの`skipped_rows`も、既存テストが「全行有効」または「有効行0件」のケースしか使っておらず、部分スキップ時の配線を検証していなかった。
- **原因分析**: テストを書く際に「この関数はテストした」という達成感で満足し、「その関数が呼ばれるべき箇所で実際に呼ばれているか」という**呼び出し側の検証**を独立した観点として意識していなかった。カバレッジ100%は「実行された行・分岐」を示すが、**関数呼び出しの引数や、その呼び出し自体が存在するかどうかを保証しない**（呼び出しを削除して別の値をそのまま使っても、多くの場合その行はカバレッジ上「実行された」ことになる）。
- **修正**: `tests/test_output_wiring.py`を新設し、10項目の配線を独立に検証するテストを追加した。CSV出力については`csv.reader`で再パースしてセル単位の値を厳密比較し（Codexレビュー「文字列の部分一致では列のずれを検出できない」という指摘に対応）、Slack通知の`timeout`は`requests.post`自体をモックして呼び出し引数を直接検証した（HTTPモック(`responses`)はワイヤー上のリクエストしか観測できず、クライアント側設定である`timeout`は検証できないため）。
- **追加した回帰テスト**: `tests/test_output_wiring.py`の10関数（詳細は`docs/test-design.md` §7参照）。**指摘された8箇所のミューテーションを実際に1つずつ手動で再現し、全て追加した配線テストが赤になること、修正を戻すと緑に戻ることを確認した**。うち2箇所（Slack本文の店舗数/商品数、構造化ログのskipped_rows）については、**既存の旧テストがミューテーション後も通過したまま**であることも実際に確認し、レビューの指摘（関数単体テストと配線検証は別物）を実証した。
- **教訓**: 「関数をテストした」と「その関数の呼び出しが正しく配線されている」は別の主張であり、別々に検証する必要がある。特に、セキュリティ・堅牢性に関わる処理（サニタイズ・エスケープ・タイムアウト設定）は、**関数単体のテストに加えて、呼び出し元の最終出力を検証するテストを必ずセットで用意する**。カバレッジの数値だけでテスト品質を語らず、「このテストは何を検知できないか」を自問する（そして可能なら実際にミューテーションを仕込んで検証する）ことが、見せかけの品質を防ぐ唯一の方法である。

### 追記（FIX-09）: プロパティテストの自己参照性も同種の欠陥として確認・対処した

`tests/test_properties.py`の性質1〜3（`total_amount`が店舗別/商品別/日付別集計の合計と一致する）も、DEF-013と同種の欠陥を抱えていた。`total_amount`と各グループ合計は**どちらも同じ`row.amount`の積み上げから計算される**ため自己参照的で、店舗別集計のグルーピングキーを取り違えても（例: 店舗別集計を誤って商品名でグルーピングしても）、**合計値は不変なため性質1〜3は成立し続けてしまう**。

実際に`aggregate()`の店舗別集計を商品キーでグルーピングするよう一時的に書き換えて検証したところ、**性質1（`test_property_total_amount_equals_sum_of_store_amounts`）は通過したまま**だった。これに対し、`aggregate()`を一切経由しない独立オラクル（最小通貨単位の整数演算で店舗ごとの真の合計を計算し直す）による新テスト`test_property_grouping_key_swap_is_detected_by_oracle`は、同じ変異を正しく検知した。`test_property_total_amount_matches_independent_oracle`（総額の独立検証）もあわせて追加した。

これは「カバレッジ100%」がテストの検知力を保証しないのと同様、「プロパティベーステストで性質を6つ検証している」という主張も、その性質同士が独立でなければ見かけ倒しになり得ることを示す実例である。

- **対応3: 性能テストの閾値が緩すぎた** — 実測(処理約1秒・ピークメモリ約52MB)に対し、閾値が30秒・500MBと**10〜30倍の余裕**があり、性能が大幅に劣化する回帰が起きても検知できない「通ることが保証された儀式」になっていた（Codex指摘）。**修正**: 実測の約3倍に閾値を厳格化（時間: 30秒→3秒、メモリ: 500MB→150MB）。新閾値で3回連続実行しフレーキーでないことを確認した。あわせてREADME・test-report.mdに残っていた古い実測値の記述（「約7秒」等、既に別コンテキストが「実測とは異なる」と指摘していた数値）も実測値に修正した。
- **教訓**: 「動くけれど何も検知していないテスト」は、テストが存在するという安心感だけを与える点でむしろ有害。assert忘れ・偶然一致・緩すぎる閾値は、レビューで名前と中身を突き合わせない限り見つからない。
